# Hybrid cores for MiSTer: what holds for every core

This file is in `hybrid/`, the [Hybrid_MiSTer](https://github.com/ItsDanik/Hybrid_MiSTer) submodule of every hybrid core repository, and each core's `CLAUDE.md` imports it. `hybrid/README.md` is the conventions document (SD card layout, OSD order, controls, behaviour, documentation); read it before changing a core's OSD, controls, launcher, packaging or README.

## Keep the cores alike

- A new core is started with `hybrid/new_core.sh` from `hybrid/template/`. Never start one by copying another core's repository.
- Before writing something in a core, check whether `hybrid/` has it. Code a second core would need as well goes into `hybrid/` (and the template, if it is a file every core has its own copy of), not into the core.
- A change to a file that came from the template is a change for every core: make it in `hybrid/template/` too, and say which existing cores still have the old version. Lines marked `GAME:` and the `CONF_STR` are the game's own.
- `hybrid/` is its own repository (branch `main`). Commit and push there first, then update the submodule pointer in the core.

## Base of a new core

- Video starts at 320x200, the core's default mode. Higher resolutions and anything else a game can do beyond that (640x200 in ECWolf, 640x400 in VanillaConquer) are extra features of that core, added once the base works. They are not part of the template.
- SDL2 games build against the static SDL2 of `hybrid/sdl2` and get video, audio and input from its "mister" drivers; the game needs a `MISTER_HYBRID` build option and a small file of its own (`hybrid/template/game/`).
- One frame per field (per two fields with an interlaced mode), timed by the core's field counter (`MH_WaitFrame()`, `MH_FieldCounter()`), not by the system clock.
- A 15kHz screen never gets more than 15kHz: 640x400 and 640x480 are interlaced at 15kHz unless the player says no such screen is there, with `forced_scandoubler=1` (VGA monitor) or the OSD option *HDMI Only*, which switches the analog output off while a progressive mode is shown. 800x600 and 1024x768 exist only then (`MH_ModeAvailable()`). `hybrid/README.md`, "Video modes".
- *HDMI Only* (status bit 0) and the *CRT Options* page (bits 64..76) are in every core's OSD, unchanged.
- Analog triggers: MiSTer gives a core no trigger axes, so `hps/mister_triggers.c` reads them from Linux (`EVIOCGABS` on every gamepad's `/dev/input/event*`; a state query works although Main_MiSTer has grabbed the device). `MH_ReadTriggers()`; in SDL axes 4 and 5 of joystick 1, 0..32767 (a game's controller mapping: `lefttrigger:+a4,righttrigger:+a5`). The furthest-pressed of all controllers: Main's player numbers cannot be seen. Which axes are the triggers is found by their resting at the bottom of their range (see the file). `tools/triggers.c` prints them on a MiSTer; `MISTER_HYBRID_TRIGGERS=l,r` fixes them for a test. Checked on a DualSense at rest only (2026-10-12), not yet pressed. The list of controllers is looked over every two seconds; a device that is no gamepad is opened once and remembered by its node (inode and time), because opening every event device again each time stopped the game for 40 to 60ms (found with the Xash3D core, 2026-10-14). Cores built before that have the stutter every two seconds: build them again.
- Stick clicks (L3, R3): MiSTer's default map passes them on as no button either, so the same file reads them (`EVIOCGKEY`, `BTN_THUMBL` / `BTN_THUMBR`, pressed on any controller): `MH_ReadStickButtons()`; in SDL buttons 30 and 31 of joystick 1 (a game's controller mapping: `leftstick:b30,rightstick:b31`). A controller whose driver names them otherwise (some generic ones) has none here. A DualSense reports both (2026-10-14). `MISTER_HYBRID_STICKBUTTONS=l,r` fixes them for a test.
- Rumble: the same file, Linux force feedback on the same devices (Main_MiSTer's grab does not stop it; Danik felt it on a DualSense, 2026-10-12). `MH_Rumble(strong, weak)`, and SDL's `SDL_JoystickRumble` / `SDL_GameControllerRumble` on joystick 1. Every controller that can rumble does. The effect is given two seconds and stored again every second while the game keeps calling, so a game that dies leaves no motor running. `tools/rumble.c` is the bare test.
- *Menu OK* / *Menu Back*: `MH_MenuButtons()` (`hps/mister_joymap.c`), which the SDL driver calls every frame, looks every two seconds whether the controllers (`/proc/bus/input/devices`), `config/` and `config/inputs/` or the mapping files it read have changed, and reads the mapping files again only then. Reading them every time stopped the game for 10 to 20ms (found with the YQuake2 core, 2026-10-15). Cores built before that have that stall every two seconds: build them again.
- *FPS Counter* (status bit 15, `"O[15],FPS Counter,Off,On;"` after *Stereo Mix*) is in every core's OSD too. The library draws it (`fps_stamp()` in `hps/mister_hybrid.c`, into the copy of the frame the core shows, RGB565 or 8bpp): a game needs no code for it, only the line in its `CONF_STR` and a build against this library. No change to the FPGA side. Cores that predate it (2026-10-12) get it at their next build: add the line. `MISTER_HYBRID_FPS=0` (or `1`) in the game's environment hides (or shows) it whatever the OSD says: for screenshots without it.
- Status bits 0..23 of the OSD mean the same in every core; a game's options start at bit 24.

## FM music

- A game whose music was made for an AdLib / OPL2 chip sends the chip's register writes to the core (`MH_FMWrite()`, host version 10; `hybrid/README.md`, "The FM chip") and does not run a software chip on the ARM, except as the fall-back for a core without the chip.
- `rtl/jtopl/` is JTOPL commit 7ac0c81 with SIX changes of ours, each marked `HYBRID:` (in `jtopl_op.v` the feedback's strength; `jtopl_eg_final.v` key scaling levels 1 and 2 swapped; `jtopl_eg_step.v` rate scaling halved, and attacks twice too fast; `jtopl_eg_ctrl.v` the release's extra half step; `jtopl_eg_pure.v` the four fastest decays; `jtopl_acc.v` a per-channel volume test its author left in). All were found by comparing with Nuked OPL3, which is taken from the chip's die: `sim/fm_song.sh <log> <out>` plays a log of register writes (`FAKECORE_FMLOG=<file>` makes fakecore write one from a running game) on both with Verilator, 25 seconds of music in 20. Do not edit `rtl/jtopl/` otherwise; when replacing it, carry the changes over or check each is no longer needed, with that tool. Still different from the chip, slightly: attack rates 1 to 3, the shape of the tremolo, and about 2dB less of the upper harmonics of a note that is dying away.

## Rules

- The launcher `launcher/danik_hybrid_cores.sh` is developed only here. Raise its `VERSION` with every change that reaches users and keep the contract in its header working for cores already released.
- Script names on the MiSTer keep the `danik_` prefix.
- MiSTer Frontier by MiSTer Organize is credited and thanked for the inspiration in every core's `README.md`, package `README.txt` and launch script header. Our launcher does not depend on it.
- Game data is never committed or shipped.
- Releases: `<Name>_YYYYMMDD.zip` from `./package.sh`, copied to `releases/` and committed. "Commit, push, release" (or just "release") also means a GitHub release, without asking: tag `<Name>_YYYYMMDD`, title `<Name> YYYYMMDD`, the zip attached, marked pre-release while the core's README calls it a beta, with notes that say what is new and how to update and install.
