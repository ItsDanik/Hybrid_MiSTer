# Hybrid cores for MiSTer: what holds for every core

This file is in `hybrid/`, the [Hybrid_MiSTer](https://github.com/ItsDanik/Hybrid_MiSTer) submodule of every hybrid core repository, and each core's `CLAUDE.md` imports it. `hybrid/README.md` is the conventions document (SD card layout, OSD order, controls, behaviour, documentation); read it before changing a core's OSD, controls, launcher, packaging or README.

## Keep the cores alike

- A new core is started with `hybrid/new_core.sh` from `hybrid/template/`. Never start one by copying another core's repository.
- Before writing something in a core, check whether `hybrid/` has it. Code a second core would need as well goes into `hybrid/` (and the template, if it is a file every core has its own copy of), not into the core.
- A change to a file that came from the template is a change for every core: make it in `hybrid/template/` too, and say which existing cores still have the old version. Lines marked `GAME:` and the `CONF_STR` are the game's own.
- `hybrid/` is its own repository (branch `main`). Commit and push there first, then update the submodule pointer in the core.
- **Every core's repository is on the branch `main`** (Danik, 2026-10-27), as `hybrid/` is: a new one is made with `git init -b main` (`new_core.sh`). The cores that were on `master` (git's default on this PC until then) were renamed that day, on GitHub too, which sends the old links on; a memory or note that says `master` for a core means `main`. A game's fork keeps its upstream's branches and its own `mister`.

## Base of a new core

- Video starts at 320x200, the core's default mode. Higher resolutions and anything else a game can do beyond that (640x200 in ECWolf, 640x400 in VanillaConquer) are extra features of that core, added once the base works. They are not part of the template. Drawing the view in 240 lines with the HUD margins (the rule below) is not one of them: a core is not finished without it, where its game allows it.
- SDL2 games build against the static SDL2 of `hybrid/sdl2` and get video, audio and input from its "mister" drivers; the game needs a `MISTER_HYBRID` build option and a small file of its own (`hybrid/template/game/`).
- One frame per field (per two fields with an interlaced mode), timed by the core's field counter (`MH_WaitFrame()`, `MH_FieldCounter()`), not by the system clock.
- **Field rate: the launchers' menus take a frame at every field of 480i** (Danik, 2026-10-27; host version 18; `hybrid/README.md`, "Video modes"). `MH_SetFieldRate(1)`: an interlaced mode then shows a new frame in every field, 59.6 pictures a second on a CRT instead of 29.8. Only dnkLauncher and ScummVM's launcher (no game running) use it, always on at 15kHz, no OSD option (option A); never a game, ScummVM's Global Main Menu neither (it is drawn at the game's resolution, so it is the game's). The core's own picture (the purple screen, the game's logo, the overlay's fades) moves at every field as well, in every core built against 18: no call for that. On HDMI without *HDMI Only* what moves there combs, which Danik accepted: every port's README says to switch on *HDMI Only* with HDMI alone (`docs/readme.md`). Every core takes it at its v18 build; only the two launchers change their code.
- **Rule: every core with interlaced output has the Flicker Filter** (Danik, 2026-10-28: "Every core that has interlaced output, should have this option in CRT Options. It should be greyed out if the signal is not interlaced"; host version 18; `hybrid/README.md`, "Video modes"). *Flicker Filter* Off (default) / Light / Strong on the *CRT Options* page after *Vertical Pos*, a blank line above it (status bits 106:105; the template's `"H9P1-;"` and `"H9DAP1O[106:105],..."`, in every core). `FLICKER` 1 in the `core/<Name>.sv` of a core with a 640x400 or 640x480 mode, 0 in every other, which hides the lines; the core greys the line out while its picture is not interlaced. The core filters a game's interlaced picture, RGB565 and 8bpp, never its own (the purple screen); Strong a quarter, half and a quarter (no blinking of one-pixel lines; RGB565 the same pixels as dnkLauncher's filter on the ARM gave, which took 4.6 ms a frame of its Carousel), Light an eighth, three quarters and an eighth (Danik, 2026-10-28: two strengths). It costs 12 M10K blocks. A game needs no code. dnkLauncher's own *Flicker filter* row and the OSD line are kept in step (Danik, 2026-10-28: `MH_FlickerFilter()`, `MH_SetFlickerFilter()`); a program filters itself only where `MH_HasFlickerFilter()` is 0. Every core with such a mode takes it at its v18 build (`FLICKER` 1, the template's lines and wiring, its README's *CRT Options* row); check it on the MiSTer: both strengths in its 640-wide modes, the line greyed in the others and with *HDMI Only*; `sim/run.sh host -DFLICK +flickeronly`.
- **Rule: the USER button and the OSD's *Reset* reset the game** (Danik, 2026-10-27: "In all other cores, by default, the OSD button [the USER button] on the MiSTer resets the game. We should implement this on all our cores"; host version 18; `hybrid/README.md`, "The game's reset"). The core shows its own picture at once (no intro again), the library ends the program within 10ms (exit code 44, `MH_EXIT_RESET`) and the launch script starts the same game again, one picked from the core's list too (`MH_PickGame()`, `MISTER_HYBRID_RESET`); nothing the game would save on quitting is saved, as on a console. A game needs no code: every core gets it at its v18 build with the template's `"R0,Reset;"` line (before *Save Diagnostic Report*), its launch script (the loop with exit code 44, `mh_message --wait-reset`) and its README's *Reset* row. Check it on the MiSTer with every game: the USER button and the OSD's line while the game runs, while it loads, in its menus and from the list; `sim/run.sh host +resetonly`.
- Frame pacing, drawing ahead (host version 12): a game whose frames take most of a field misses vblanks with the slightly slower ones, the frame before shown twice and that one never, which the game's frames-per-field count does not show (Xash3D, 2026-10-15: 14ms frames of 16.8, 5 to 8 times a second). Drawn a field ahead, the frame for field F from counter F - 2 and presented with `MH_PresentAtField(F)`, one may take longer than a field; it costs one field of latency. The template has it behind `DRAW_AHEAD` (`template/game/mister_port.c`), off; a game whose frames are late in some modes only draws ahead in those alone, `MiSTer_SetDrawAhead()` every frame (TheForceEngine's 640-wide modes, 2026-10-26; cores from before have no such function, and need none until then). `MISTER_HYBRID_PACE=1` prints the frames never shown and shown twice; `MISTER_HYBRID_AHEAD=0` makes `MH_PresentAtField()` do nothing, which is the old way.
- **Rule: when a game is built against the framework** (a new core, or an existing one built again with host version 12 or later), build it with `DRAW_AHEAD` 1 and run one or two benchmarks of a heavy scene on the MiSTer with `MISTER_HYBRID_PACE=1`, once with `MISTER_HYBRID_AHEAD=0` and once without, in turns. Keep drawing ahead only if it takes the frames shown twice or never down by a clear margin; otherwise `DRAW_AHEAD` 0, for the lower latency. Write the numbers and the decision in the core's `CLAUDE.md`.
- A 15kHz screen never gets more than 15kHz: 640x400 and 640x480 are interlaced at 15kHz unless the player says no such screen is there, with `forced_scandoubler=1` (VGA monitor) or the OSD option *HDMI Only*, which switches the analog output off while a progressive mode is shown. `hybrid/README.md`, "Video modes". 800x600 and 1024x768 are gone since host version 13 (they made every build longer and few games used them): no game offers them, and a game whose own code lists them must not be able to pick them.
- **Rule: 240 lines and HUD margins.** A game whose view can be drawn in 240 lines (320x240, or 640x480 for a 640-wide game) offers that, as a mode of its own; the 200-line modes it has stay (some games draw in 200 lines and should: ECWolf keeps 320x200 and 640x200 next to 320x240 and 640x240). In 240 lines the extra lines go to the view, never to scaling: the view fills the screen from the top edge to the bottom one, and the HUD keeps its size and is drawn over it where the player's HUD margins put it, the view going on behind and around it (no black or filled strip below a status bar). The margins are read every frame (`MH_HudMargins()`, or `MiSTer_HudRows()` of `template/game/mister_port.c`) and applied at once: *HUD (Top)* / *HUD (Bottom)* on the *CRT Options* page (status bits 77..81 and 82..86, 0..24 pixels of a 240-line screen; `hybrid/README.md`, "HUD margins"). **Both margins are 0 by default** (Danik, 2026-10-21: any other default confused players without overscan, who see every pixel; host version 16, entry n is n pixels, up to 15 entry 0 was 10). No hardcoded HUD offsets for a particular screen. **A game with a HUD has both lines, the one of an edge it has no HUD at greyed out** (Danik, 2026-10-21; ECWolf: *HUD (Top)* greyed out). **Ask Danik how a new core's HUD margins are to work** (which edges have a HUD, and what moves with each margin), in the plan made before building, as for its cheats (Danik, 2026-10-21). Decided for the existing cores (2026-10-21): Dethrace, OpenScreamer and Xash3D top and bottom; ECWolf, jfSW and YQuake2 bottom only, ReNFS too (Danik, 2026-10-22: its status bar stays where the game has it) (YQuake2 had both lines up to then); CrispyDoom not yet, ask at its next build; Shockolate has none (Danik, 2026-10-23: it stays in 320x200, its panelled view one picture that cannot grow; its `CLAUDE.md`). The lines: the core's `HUD_EDGES` (`template/core/@NAME@.sv`) sets menu mask bits 7 / 8 for the `D7` / `D8` in front of the lines, so they are greyed out before the game runs; a game without a HUD has neither, nor the `"P1-;"` above them; the game greys them out (`MH_SetMenuMask()`) while a 200-line mode is used, and in a core with several games greys out (no longer hides) the line of an edge a game has no HUD at. Full-screen artwork is never scaled but by whole numbers (the 640-wide modes): in 240 lines it stays centred. This holds for every core: a new one, and every existing one when it is built again against host version 13 or later, the default of 0 and the greyed-out line when built against 16 or later (it takes the template's two lines and `HUD_EDGES`; a player who had set a margin other than 10 sets it again) (check whether it already does; if its view cannot be drawn in 240 lines, it stays in 200, centred, without the HUD lines, and its `CLAUDE.md` says why). Test with `MISTER_HYBRID_HUD=0,0` and `24,24` and on the MiSTer by changing the options while the game runs.
- *HDMI Only* (status bit 1) and the *CRT Options* page (bits 64..76) are in every core's OSD, unchanged. Never put an option on status bit 0: Main_MiSTer sets it while it loads a core (the reset) and clears it after, so the option would be off after every load. *HDMI Only* was there up to host version 12 and was lost that way; a core built again with this template has it on bit 1 (its `core/<Name>.sv` takes the two lines from the template).
- Analog triggers: MiSTer gives a core no trigger axes, so `hps/mister_triggers.c` reads them from Linux (`EVIOCGABS` on every gamepad's `/dev/input/event*`; a state query works although Main_MiSTer has grabbed the device). `MH_ReadTriggers()`; in SDL axes 4 and 5 of joystick 1, 0..32767 (a game's controller mapping: `lefttrigger:+a4,righttrigger:+a5`). The furthest-pressed of all controllers: Main's player numbers cannot be seen. Which axes are the triggers is found by their resting at the bottom of their range (see the file). `tools/triggers.c` prints them on a MiSTer; `MISTER_HYBRID_TRIGGERS=l,r` fixes them for a test. Checked on a DualSense at rest only (2026-10-12), not yet pressed. Z / RZ and RX / RY are triggers only on a controller with both pairs, while the other pair (its right stick) is in the middle (2026-10-21): a Switch Pro Controller has RX / RY alone, its right stick, which was taken for the triggers once pushed up and left, and then held fire and run. Cores built before: build them again. The list of controllers is looked over every two seconds; a device that is no gamepad is opened once and remembered by its node (inode and time), because opening every event device again each time stopped the game for 40 to 60ms (found with the Xash3D core, 2026-10-14). Cores built before that have the stutter every two seconds: build them again.
- Racing wheels: their pedals are the triggers too (`MH_ReadTriggers()`: gas the right one, brake the left). Main_MiSTer knows a list of wheels by vendor and product (`setup_wheels` in its `input.cpp`: Logitech G25 / G27 / G29 / Driving Force / DFP / DFGT, Fanatec, Thrustmaster and others) and hands a core their axes itself, whatever the model: the wheel on the left stick's X (full range), the gas on the left stick's Y and the brake on the right stick's, 0 let go to -127 pressed. For a wheel of that list (`is_wheel()`, the same list, 2026-10-16) the library takes the pedals from the core's sticks (it needs `MH_Open()`), not from the wheel's own axes; a wheel outside the list is a plain controller. While such a wheel is connected, a gamepad's stick pushed up counts as a pedal too, and the gas pedal moves a menu's line like the stick up. Main_MiSTer makes a wheel whichever player it comes as, often player 2 next to a gamepad: while one is connected (`MH_WheelConnected()`), the SDL driver's joystick 1 is both players' controllers, each stick axis the one further out, the buttons and the d-pad of either (2026-10-19; a game reading `MH_ReadInput()` itself does the same, as Dethrace's `apply_analog()`). Cores built before steer with a wheel only when it is player 1: build them again. Tested on the MiSTer with a virtual G29 through uinput (Main gives it a player with a button of its default map, BTN_SOUTH): full gas and brake 254, half the brake 128, the wheel turned left -127; not yet with a real wheel. `tools/triggers.c` with `MISTER_HYBRID_CORE=<core>` attaches and prints the core's sticks too.
- **A core loaded again is seen however long the game did not look** (2026-10-25, CrispyDoom): `MH_CheckAlive()` took its first count at its first call and took a reload only for a count that went back, so a reload while a game loaded its data (seconds without a look) went unseen: the game went on with the new core showing its own picture over the game's. It counts from `MH_Open()` now, and a count that went on by less than the time since the last look (more than half a second and 5% short at 59Hz) is a reload too; a count that stands still is a core gone, as before. A count that went back, or the core's mark gone, is seen at every call, not only every half second (the name and the slow count still are): a game whose clock is the count read it right after the reload, below its count at the start, and CrispyDoom's clock jumped 2^32 fields ahead, its title screens waiting for ever for the next tic while the core said "Game not running" (Danik's reload of the MGL from the OSD, 10 s in). A game's clock never takes a count lower than the one before (`MiSTer_TimeUS()` of CrispyDoom). Cores built before: build them again.
- `MH_Open()` pins the game thread to CPU0 and puts the helper threads (the frame copy, audio) on CPU1, if both CPUs are allowed; `MH_Close()` gives the thread back the CPUs it had (2026-10-21). Before, a program started with `execv()` after `MH_Close()` inherited CPU0 alone and ran without helper threads: CrispyDoom's Heretic, Hexen and Strife copied every frame to the FPGA on the game thread, 11 to 13% of its time at 640x240. A core that starts another program that way is built again.
- SDL's resampler (`SDL_ConvertAudio()`, audio streams of another rate than the core's) is patched in `sdl2/integrate.py` (2026-10-21): no 64-bit division per frame (none in hardware on the ARM) and the filter worked out once per fraction of a source frame, then the same floats added up in the same order, so the same sound (every sound of DOOM2.WAD and PLUTONIA.WAD compared). CrispyDoom's sounds, converted at its start, took 6.5s on the MiSTer and take 2.0. A patch's replacement text must change when the patch does: `integrate.py` skips a patch whose replacement is already there, and an anchor that is still there after an earlier version was applied gets it a second time (take the file fresh from the tarball then). Cores get it at their next build.
- Stick clicks (L3, R3): MiSTer's default map passes them on as no button either, so the same file reads them (`EVIOCGKEY`, `BTN_THUMBL` / `BTN_THUMBR`, pressed on any controller): `MH_ReadStickButtons()`; in SDL buttons 30 and 31 of joystick 1 (a game's controller mapping: `leftstick:b30,rightstick:b31`). A controller whose driver names them otherwise (some generic ones) has none here. A DualSense reports both (2026-10-14). `MISTER_HYBRID_STICKBUTTONS=l,r` fixes them for a test.
- **Rule: in a first-person game the left stick only moves and strafes** (Danik, 2026-10-25: "make sure that when the player tilts fully the left analog stick, the player does only strafe and not turn. Make this a rule for all FPS games"). Main_MiSTer presses the d-pad as well when a stick is pushed far (a digital pad for every core; `status.py` shows the d-pad bit with the stick's analog value), so where the d-pad turns (or switches weapons, uses the inventory) a full tilt of the left stick strafed and turned at once. In play a d-pad direction the left stick points in is not the d-pad's: `MH_StickDpad(lx, ly)` (`hps/mister_hybrid.h`; an SDL axis `>> 8`) gives the directions to drop, a quarter of the way out or more. The menus keep them (the stick moves through a menu as the d-pad does). Every FPS core, new or built again: check it on the MiSTer with the stick pushed fully left and right, slowly and fast. Cores that had it before, each its own code: CrispyDoom (`MISTER_STICK_PAD`), DXX-Rebirth (`joy_mister_dpad_from_stick()`), YQuake2 and Xash3D (`MiSTer_StickHoldsDpad()`); ChocolateQuake has its own too (`in_gamepad.c`). Danik checked every FPS core on the MiSTer (2026-10-26): all of them only move and strafe with the left stick, jfSW, EDuke32 and ECWolf without code of their own for it.
- Rumble: the same file, Linux force feedback on the same devices (Main_MiSTer's grab does not stop it; Danik felt it on a DualSense, 2026-10-12). `MH_Rumble(strong, weak)`, and SDL's `SDL_JoystickRumble` / `SDL_GameControllerRumble` on joystick 1. Every controller that can rumble does. The effect is given two seconds and stored again every second while the game keeps calling, so a game that dies leaves no motor running. `tools/rumble.c` is the bare test.
- *Menu OK* / *Menu Back* are the MiSTer menu's own (Danik, 2026-10-18; host version 14): for each controller its Menu OK / Menu Back of Main_MiSTer's *Define joystick buttons*, else the A / B of its mapping there, as the MiSTer menu has them. A controller without a mapping confirms and goes back as on its console: Nintendo (vendor `057e`, 8BitDo pads in Switch mode too) the right button and the bottom one, every other (PlayStation, Xbox) the bottom one and the right one (`convention_codes()`; the Nintendo case not yet tried with a real controller). The OSD options *Menu OK* / *Menu Back* that picked other buttons are gone; status bits 16..23 stay unused (16 *Save Diagnostic Report* since host version 16), a rebuilt core's saved settings may still have them set. A core built again with host version 14 takes the template's lines: no `O[19:16]` / `O[23:20]` and the `"-;"` after them, and `.osd_open(OSD_STATUS)` for `hybrid_host`.
- **Nothing reaches the game while the OSD menu is open** (Danik, 2026-10-18; host version 14). Main_MiSTer passes the core no buttons and keys then, but what the library reads from Linux itself (the physical Menu OK / Back, triggers, stick clicks) knows nothing of the OSD: Screamer 2's menus confirmed and went back with the OSD's Cross and Circle. The core puts `OSD_STATUS` (1 for the OSD menu, not its info boxes) in bit 22 of the status word 1, `MH_OSDOpen()`, and the library holds everything back meanwhile: in `MH_ReadInput()` (buttons, keys, sticks, mouse buttons; the mouse's movement left out) and in the Linux reads (`mh_osd_hold()`); what is held when the OSD closes stays released until it is let go. A game needs no code for it. Cores built before have the leak: build them again.
- *Menu OK* / *Menu Back*: `MH_MenuButtons()` (`hps/mister_joymap.c`), which the SDL driver calls every frame, looks every two seconds whether the controllers (`/proc/bus/input/devices`), `config/` and `config/inputs/` or the mapping files it read have changed, and reads the mapping files again only then. Reading them every time stopped the game for 10 to 20ms (found with the YQuake2 core, 2026-10-15). Cores built before that have that stall every two seconds: build them again. The mapping files are found under the name Main_MiSTer loaded (`MH_MappingName()`, `/tmp/CORENAME`), not `MISTER_HYBRID_SET`. A physical OK / Back button that drives no core button (one without a function in that core, which MiSTer then passes to the core not at all) is read from Linux, as the stick buttons are: `MH_MenuButtonsPressed()`, which the SDL driver uses for its Menu OK / Menu Back buttons (found with Dethrace on a DualSense, 2026-10-16: Back on Circle, which had no race function). Cores built before have no Menu Back on such a button: build them again. A controller is a device of `/proc/bus/input/devices` with a `js` handler, or with a stick or hat and a gamepad's buttons (`BTN_JOYSTICK`..`BTN_DIGI`): a Switch Pro Controller of hid-nintendo has no `js` handler on the MiSTer, only Zaparoo's virtual pad was found, and Menu OK / Back were no button at all (CrispyDoom issue #2, 2026-10-22; tested on the PC with a copy of such a list). A menu mapping with neither OK / Back nor A / B (Zaparoo's has its axes alone) counts as none. Cores built before: build them again.
- *FPS Counter* (status bit 15, `"O[15],FPS Counter,Off,On;"` after *Stereo Mix*) is in every core's OSD too. The library draws it (`fps_stamp()` in `hps/mister_hybrid.c`, into the copy of the frame the core shows, RGB565 or 8bpp): a game needs no code for it, only the line in its `CONF_STR` and a build against this library. No change to the FPGA side. Cores that predate it (2026-10-12) get it at their next build: add the line. `MISTER_HYBRID_FPS=0` (or `1`) in the game's environment hides (or shows) it whatever the OSD says: for screenshots without it.
- **Rule: every core has the diagnostic report** (Danik, 2026-10-21; host version 16; `docs/diagnostics.md`, `hybrid/README.md` "Diagnostic report"). *Save Diagnostic Report* (`"-;"`, `"T[16],Save Diagnostic Report;"`) is the last line of every core's OSD, before `J1`, and the template's `"I,"` line with its texts 17 and 18 is in every core, one without MIDI too. The library does the rest (`hps/mister_diag.c`: a record of the last 60 seconds kept all the time, the zip in `games/dnk/diagnostics/`, the info box); a game needs no code, and may add a file with `MH_DiagAdd()`. Nothing goes into a report that identifies the player or their network (no network files, addresses, Bluetooth ids, saved games, folder listings); a `MiSTer.ini` key joins `ini_keys` only if it bears on video, audio or input. A core built again with host version 16 takes the lines from the template, and its README the section *If something is wrong*. Check it on the MiSTer with each core: pick the line while the game runs, read the zip with `tools/diag_read.py`.
- Status bits 0..23 of the OSD mean the same in every core (16..23 unused since host version 14; 16 *Save Diagnostic Report*, a trigger, since host version 16); a game's options start at bit 24. Triggers (`T`, a cheat, "next level") are bits 56..59 only, read with `MH_OSDTriggers()`: a trigger's pulse is too short for the game to see, the core flips the bit instead.
- A core with several games picks one with `MH_PickGame()` (`hybrid/README.md`, "Several games in one core"): each game a menu entry (set name `<core>_<id>`), shareware without one; the list only of the games that are there. Settings and button mappings are per game (`MH_SetName()`).
- **Rule: the purple screen ignores *Horizontal Size*** (Danik, 2026-10-16). The core's own picture (logo, messages, game lists) is always shown at size 0, whatever the player set on the *CRT Options* page for the game: nothing is at its edges, and a small size makes its text hard to read. `hybrid_host.sv` takes the size only while a game has the screen (`game_on`); the positions still apply. Keep it that way in any change to the video timing, and test the core's picture with the size at -24 when it changes.
- **Rule: messages fit in 4 lines of 71 characters** (`MH_MSG_ROWS`, `MH_MSG_COLS`; `hybrid/README.md`, "Messages"). Every message a game shows (`MH_UI_Message()`, `MiSTer_ShowError()`) is written for that space: what is wrong and what to do, with the path from where the game runs (`games/dnk/<Engine>/`), no empty lines. Check each one with `tools/make_wall.py --preview out.png --message "..."` when a core is built against host version 13 or later; messages of cores from before were written for 36 characters and empty lines and need going over.
- **Rule: every port starts the same way** (Danik, 2026-10-16: "a UX as unified as possible"). The core's purple screen with its intro; the game waits for the intro's end (the library does). The game is the menu entry's (`MH_PickGame()`), or from the core's list of the games that are there when the core was started by itself (one there: that one; none: the message naming the files and where they go). From the moment the game is known until its first frame the purple screen says **`Loading <title>...`**, the title as in `package/games.txt` (`MH_UI_Message(title, text, 0)` right after `MH_PickGame()`, as `MiSTer_PickGame()` of `template/game/mister_port.c` does; a port with its own pick code adds it). Quitting a game picked from the list brings the list back (exit code 42), otherwise the MiSTer menu. Check it on the MiSTer for every game with `tools/test_on_mister.sh`. **From host version 17 the game's logo** (Danik, 2026-10-22; `docs/game_logo.md`, `hybrid/README.md` "The game's logo"): once the intro is over "Checking Game Data..." and "Game Data OK" come under the MiSTer logo, each at least 0.4 seconds; the MiSTer logo goes with them, "Loading <title>..." comes in the first row while the screen is empty, and the game's logo in the MiSTer logo's place (440x200, centred, its bottom edge on the MiSTer logo's, rising 16 pixels while it fades in); it stays at least 2 seconds before the game's first frame. The game's logo means the game is starting (Danik, 2026-10-23): data missing, the message naming the files takes "Checking Game Data..."'s place under the MiSTer logo and no game logo comes; a core started by itself shows the list under the MiSTer logo first. `MH_PickGame()` does it; the template's `MiSTer_PickGame()` no longer shows "Loading <title>..." itself (every core before host version 17 still does: it takes the template's function when it is built against 17). **Every game of `package/games.txt` has its logo, `package/logos/<id>.png`**: a core cannot be built against host version 17 without them (`package.sh` refuses). Ask Danik for them before a core is built against 17. **This start, its lines and their order are the same in every core** (Danik, 2026-10-23: "a rule that all cores adopt"): every core, new or built again, takes it from the library (`MH_PickGame()`, or `MH_GameLogo()` / `MH_GameLogoLoading()` / `MH_GameLogoMissing()` in a port with pick code of its own) and shows nothing of its own on the purple screen from the pick to its first frame (no "Loading" message, no message of its own before the data check's lines); the texts and timings are the library's alone (`logo_text`, `LOGO_*` in `hps/mister_hybrid.c`), never changed in one core. A change to them is made here, for every core, and the cores take it at their next build. ## FM music and MIDI

- A game whose music was made for an AdLib / OPL2 chip sends the chip's register writes to the core (`MH_FMWrite()`, host version 10; `hybrid/README.md`, "The FM chip") and does not run a software chip on the ARM, except as the fall-back for a core without the chip.
- **MT32-pi** (host version 15; Danik, 2026-10-20, for CrispyDoom and jfSW; `hybrid/README.md`, "MIDI and the MT32-pi"): a game with General MIDI music sends it with `MH_MidiEvent()` while `MH_MidiWanted()`, to an MT32-pi on the user port through MiSTer's `sys/mt32pi.sv`; its OSD lines (status bits 96..103) are shown only while one is connected. The game API is the in-core synthesizer's (below) so the games need no second path. Danik has none; a tester tried the test zips (2026-10-20): Doom's music on the Pi, the OSD lines, the synth switches, the volume and HDMI audio work; unplugging was not noticed (`mt32pi.sv` keeps `mt32_available` until a reset), so the core now takes a second without a poll for "gone" (`MT32_QUIET`); and the OSD's SoundFont 0..7 replaced the Pi's own at every start, the core now sends back the one the Pi reports unless the OSD names one (*Pi's own*, the default); and after a SoundFont switch the music played with the wrong instruments (the Pi starts it with none of the song's settings): the game sends them again after `MH_MidiSynthChanged()`, and *Reset Hanging Notes* (bit 104) was asked for. The third test build was confirmed in full (2026-10-21): all of CrispyDoom's games and jfSW's shareware, on a real Pi. Tested in `sim/tb_host.sv` (a stand-in Pi: I2C, I2S, the UART's bytes and their frames) and with `fakecore` (`FAKECORE_MT32`, `FAKECORE_MIDILOG`). A song's first notes were cut short on the Pi (a player, CrispyDoom, 2026-10-23): the reset and the settings sent before them are a burst on the 31250 baud cable, and the notes went out behind it while their ends came nearly on time. `MH_MidiBacklog()` (the library follows the cable in audio frames) is how long a game holds a song's first events back: at a song's start, after a seek or a pause, after `MH_MidiSynthChanged()`. CrispyDoom, jfSW and the MIDI Player use it; check with `tools/midilog_wire.py` on a `FAKECORE_MIDILOG`.
- **MIDI synthesizer in the core** (host version 16; `docs/midi_synth.md`, its decisions and phases): 128 voices of SoundFont 2 from the DDR3 with FluidSynth's reverb (Freeverb) and chorus (`rtl/hybrid_midi*.sv`, the effects `hybrid_midi_fx.sv`; its own 100MHz PLL), sample-exact with the C model `tools/midisynth/midisynth.c` (`sim/midi_engine.sh` checks it in Verilator; fix whichever is wrong, never the test). The library works out the voices (`hps/mister_midi.c`) and writes commands to the MIDI ring (0x030000). Merged onto the MT32-pi as Danik chose (2026-10-21): both menus stay, *Music* MIDI / FM chip (bit 87) and *SoundFont* (88..90) next to the Pi's lines; with *Music* on MIDI the music goes to the Pi when one is connected and on, else to the synthesizer; a switch between them makes `MH_MidiSynthChanged()` 1 and the game resends the song's settings; a SoundFont change in the synthesizer keeps the channels. Info texts: 1..13 the Pi's, 14..16 the SoundFont's errors, a game's own from 24. Only GeneralUser GS is shipped (`games/dnk/SoundFonts/`); a player adds others at their own responsibility. A core of host version 15 or older reports no synthesizer (`status[3] < 16`): `MH_MidiWanted()` is then the Pi's alone. OSD bits 87..95 are the synthesizer's (87 *Music*, 88..90 *SoundFont*, 91..95 kept for later MIDI options); info texts 17 and 18 are the diagnostic report's. Size (2026-10-21): about 9,500 ALMs, 316 M10K blocks and 20 DSP blocks with the effects; CrispyDoom with it 54% of the logic, 82% of the M10K, 92% of the DSP blocks, timing met with about 0.1 ns at 100 MHz, so a change to the synthesizer's RTL is fitted in a scratch core and its timing checked before it is committed. **Only a core whose games play MIDI has it** (Danik, 2026-10-22): `MIDI_SYNTH` 1 in its `core/<Name>.sv` (the template's `GAME:` line, with the *Music* / *SoundFont* lines), 0 in every other core, which then has no synthesizer and no 100MHz PLL (status word 1 bit 28; `MH_MidiWanted()` the Pi's alone; `FAKECORE_SYNTH=0` on the PC; `sim/tb_host.sv` with `-DNO_SYNTH`). Ask Danik at each core's v16 build whether its games play MIDI.
- **Rule: every port whose games play MIDI brings the SoundFont** (Danik, 2026-10-22). A core with `MIDI_SYNTH` 1 has GeneralUser GS in its zip: `games/dnk/SoundFonts/GeneralUser-GS.sf2` and its licence, `GeneralUser-GS-LICENSE.txt`, next to it. The template's `package.sh` does it (`hybrid/tools/soundfont.sh`): it downloads the font from its author's GitHub at the commit pinned in that script, checks both files' SHA-256 and keeps them in the core's `build/soundfont/`. The font is never committed to a core's repository or this one; the database's repository (`dnk_Distribution_MiSTer`) holds the one copy players get. `distribution.py` stores it once in the database, in `shared.txt` with every port that brings it, tagged with all their tags; it refuses a zip whose copy is not the same bytes as the other ports', so a new version (the commit, sums and sizes in `soundfont.sh`, its licence read again) means packaging every port with MIDI again. A port's README says the font comes with it and credits it. A core built again with MIDI takes the template's `package.sh` lines; CrispyDoom and the MIDI Player have them (2026-10-22), jfSW too (2026-10-23). A zip never carries `games/dnk/SoundFonts/slots.txt`, the player's.
- `rtl/jtopl/` is JTOPL commit 7ac0c81 with SIX changes of ours, each marked `HYBRID:` (in `jtopl_op.v` the feedback's strength; `jtopl_eg_final.v` key scaling levels 1 and 2 swapped; `jtopl_eg_step.v` rate scaling halved, and attacks twice too fast; `jtopl_eg_ctrl.v` the release's extra half step; `jtopl_eg_pure.v` the four fastest decays; `jtopl_acc.v` a per-channel volume test its author left in). All were found by comparing with Nuked OPL3, which is taken from the chip's die: `sim/fm_song.sh <log> <out>` plays a log of register writes (`FAKECORE_FMLOG=<file>` makes fakecore write one from a running game) on both with Verilator, 25 seconds of music in 20. Do not edit `rtl/jtopl/` otherwise; when replacing it, carry the changes over or check each is no longer needed, with that tool. Still different from the chip, slightly: attack rates 1 to 3, the shape of the tremolo, and about 2dB less of the upper harmonics of a note that is dying away.

Test changes on a copy of an SD card (`DANIK_HYBRID_ROOT`, `DANIK_HYBRID_TMP`), on the PC and in `/tmp` on the MiSTer, never on the player's own setup.

A new long job's script gets the two lines `sim/run.sh` has (the `exec` through `job.sh`, the `dnk.job` label on its `docker run`). `build_core.sh` is the template's: a core with the old one (all before 2026-10-23) takes no slot, `jobs.py` shows its build with a `*`; it takes the template's lines when it is built again, with a `hybrid/` that has `job.sh`.
