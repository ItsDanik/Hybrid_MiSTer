# Hybrid cores for MiSTer: what holds for every core

This file is in `hybrid/`, the [Hybrid_MiSTer](https://github.com/ItsDanik/Hybrid_MiSTer) submodule of every hybrid core repository, and each core's `CLAUDE.md` imports it. `hybrid/README.md` is the conventions document (SD card layout, OSD order, controls, behaviour, documentation); read it before changing a core's OSD, controls, launcher, packaging or README.

## Keep the cores alike

- A new core is started with `hybrid/new_core.sh` from `hybrid/template/`. Never start one by copying another core's repository.
- Before writing something in a core, check whether `hybrid/` has it. Code a second core would need as well goes into `hybrid/` (and the template, if it is a file every core has its own copy of), not into the core.
- A change to a file that came from the template is a change for every core: make it in `hybrid/template/` too, and say which existing cores still have the old version. Lines marked `GAME:` and the `CONF_STR` are the game's own.
- `hybrid/` is its own repository (branch `main`). Commit and push there first, then update the submodule pointer in the core.

## Base of a new core

- Video starts at 320x200, the core's default mode. Higher resolutions and anything else a game can do beyond that (640x200 in ECWolf, 640x400 in VanillaConquer) are extra features of that core, added once the base works. They are not part of the template. Drawing the view in 240 lines with the HUD margins (the rule below) is not one of them: a core is not finished without it, where its game allows it.
- SDL2 games build against the static SDL2 of `hybrid/sdl2` and get video, audio and input from its "mister" drivers; the game needs a `MISTER_HYBRID` build option and a small file of its own (`hybrid/template/game/`).
- One frame per field (per two fields with an interlaced mode), timed by the core's field counter (`MH_WaitFrame()`, `MH_FieldCounter()`), not by the system clock.
- Frame pacing, drawing ahead (host version 12): a game whose frames take most of a field misses vblanks with the slightly slower ones, the frame before shown twice and that one never, which the game's frames-per-field count does not show (Xash3D, 2026-10-15: 14ms frames of 16.8, 5 to 8 times a second). Drawn a field ahead, the frame for field F from counter F - 2 and presented with `MH_PresentAtField(F)`, one may take longer than a field; it costs one field of latency. The template has it behind `DRAW_AHEAD` (`template/game/mister_port.c`), off. `MISTER_HYBRID_PACE=1` prints the frames never shown and shown twice; `MISTER_HYBRID_AHEAD=0` makes `MH_PresentAtField()` do nothing, which is the old way.
- **Rule: when a game is built against the framework** (a new core, or an existing one built again with host version 12 or later), build it with `DRAW_AHEAD` 1 and run one or two benchmarks of a heavy scene on the MiSTer with `MISTER_HYBRID_PACE=1`, once with `MISTER_HYBRID_AHEAD=0` and once without, in turns. Keep drawing ahead only if it takes the frames shown twice or never down by a clear margin; otherwise `DRAW_AHEAD` 0, for the lower latency. Write the numbers and the decision in the core's `CLAUDE.md`.
- A 15kHz screen never gets more than 15kHz: 640x400 and 640x480 are interlaced at 15kHz unless the player says no such screen is there, with `forced_scandoubler=1` (VGA monitor) or the OSD option *HDMI Only*, which switches the analog output off while a progressive mode is shown. `hybrid/README.md`, "Video modes". 800x600 and 1024x768 are gone since host version 13 (they made every build longer and few games used them): no game offers them, and a game whose own code lists them must not be able to pick them.
- **Rule: 240 lines and HUD margins.** A game whose view can be drawn in 240 lines (320x240, or 640x480 for a 640-wide game) offers that, as a mode of its own; the 200-line modes it has stay (some games draw in 200 lines and should: ECWolf keeps 320x200 and 640x200 next to 320x240 and 640x240). In 240 lines the extra lines go to the view, never to scaling: the view fills the screen from the top edge to the bottom one, and the HUD keeps its size and is drawn over it where the player's HUD margins put it, the view going on behind and around it (no black or filled strip below a status bar). The margins are read every frame (`MH_HudMargins()`, or `MiSTer_HudRows()` of `template/game/mister_port.c`) and applied at once: *HUD (Top)* / *HUD (Bottom)* on the *CRT Options* page (status bits 77..81 and 82..86, 0..24 pixels of a 240-line screen, 10 by default; `hybrid/README.md`, "HUD margins"). No hardcoded HUD offsets for a particular screen. The core's `CONF_STR` has the line of each edge the game has a HUD at and not the others (ECWolf: *HUD (Bottom)* only); a game without a HUD has neither, nor the `"P1-;"` above them; the game greys them out (`MH_SetMenuMask()`) while a 200-line mode is used, and in a core with several games hides the line a game has no HUD for. Full-screen artwork is never scaled but by whole numbers (the 640-wide modes): in 240 lines it stays centred. This holds for every core: a new one, and every existing one when it is built again against host version 13 or later (check whether it already does; if its view cannot be drawn in 240 lines, it stays in 200, centred, without the HUD lines, and its `CLAUDE.md` says why). Test with `MISTER_HYBRID_HUD=0,0` and `24,24` and on the MiSTer by changing the options while the game runs.
- *HDMI Only* (status bit 1) and the *CRT Options* page (bits 64..76) are in every core's OSD, unchanged. Never put an option on status bit 0: Main_MiSTer sets it while it loads a core (the reset) and clears it after, so the option would be off after every load. *HDMI Only* was there up to host version 12 and was lost that way; a core built again with this template has it on bit 1 (its `core/<Name>.sv` takes the two lines from the template).
- Analog triggers: MiSTer gives a core no trigger axes, so `hps/mister_triggers.c` reads them from Linux (`EVIOCGABS` on every gamepad's `/dev/input/event*`; a state query works although Main_MiSTer has grabbed the device). `MH_ReadTriggers()`; in SDL axes 4 and 5 of joystick 1, 0..32767 (a game's controller mapping: `lefttrigger:+a4,righttrigger:+a5`). The furthest-pressed of all controllers: Main's player numbers cannot be seen. Which axes are the triggers is found by their resting at the bottom of their range (see the file). `tools/triggers.c` prints them on a MiSTer; `MISTER_HYBRID_TRIGGERS=l,r` fixes them for a test. Checked on a DualSense at rest only (2026-10-12), not yet pressed. The list of controllers is looked over every two seconds; a device that is no gamepad is opened once and remembered by its node (inode and time), because opening every event device again each time stopped the game for 40 to 60ms (found with the Xash3D core, 2026-10-14). Cores built before that have the stutter every two seconds: build them again.
- Racing wheels: their pedals are the triggers too (`MH_ReadTriggers()`: gas the right one, brake the left). Main_MiSTer knows a list of wheels by vendor and product (`setup_wheels` in its `input.cpp`: Logitech G25 / G27 / G29 / Driving Force / DFP / DFGT, Fanatec, Thrustmaster and others) and hands a core their axes itself, whatever the model: the wheel on the left stick's X (full range), the gas on the left stick's Y and the brake on the right stick's, 0 let go to -127 pressed. For a wheel of that list (`is_wheel()`, the same list, 2026-10-16) the library takes the pedals from the core's sticks (it needs `MH_Open()`), not from the wheel's own axes; a wheel outside the list is a plain controller. While such a wheel is connected, a gamepad's stick pushed up counts as a pedal too, and the gas pedal moves a menu's line like the stick up. Tested on the MiSTer with a virtual G29 through uinput (Main gives it a player with a button of its default map, BTN_SOUTH): full gas and brake 254, half the brake 128, the wheel turned left -127; not yet with a real wheel. `tools/triggers.c` with `MISTER_HYBRID_CORE=<core>` attaches and prints the core's sticks too.
- Stick clicks (L3, R3): MiSTer's default map passes them on as no button either, so the same file reads them (`EVIOCGKEY`, `BTN_THUMBL` / `BTN_THUMBR`, pressed on any controller): `MH_ReadStickButtons()`; in SDL buttons 30 and 31 of joystick 1 (a game's controller mapping: `leftstick:b30,rightstick:b31`). A controller whose driver names them otherwise (some generic ones) has none here. A DualSense reports both (2026-10-14). `MISTER_HYBRID_STICKBUTTONS=l,r` fixes them for a test.
- Rumble: the same file, Linux force feedback on the same devices (Main_MiSTer's grab does not stop it; Danik felt it on a DualSense, 2026-10-12). `MH_Rumble(strong, weak)`, and SDL's `SDL_JoystickRumble` / `SDL_GameControllerRumble` on joystick 1. Every controller that can rumble does. The effect is given two seconds and stored again every second while the game keeps calling, so a game that dies leaves no motor running. `tools/rumble.c` is the bare test.
- *Menu OK* / *Menu Back* are the MiSTer menu's own (Danik, 2026-10-18; host version 14): for each controller its Menu OK / Menu Back of Main_MiSTer's *Define joystick buttons*, else the A / B of its mapping there, as the MiSTer menu has them. A controller without a mapping confirms and goes back as on its console: Nintendo (vendor `057e`, 8BitDo pads in Switch mode too) the right button and the bottom one, every other (PlayStation, Xbox) the bottom one and the right one (`convention_codes()`; the Nintendo case not yet tried with a real controller). The OSD options *Menu OK* / *Menu Back* that picked other buttons are gone; status bits 16..23 stay unused, a rebuilt core's saved settings may still have them set. A core built again with host version 14 takes the template's lines: no `O[19:16]` / `O[23:20]` and the `"-;"` after them, and `.osd_open(OSD_STATUS)` for `hybrid_host`.
- **Nothing reaches the game while the OSD menu is open** (Danik, 2026-10-18; host version 14). Main_MiSTer passes the core no buttons and keys then, but what the library reads from Linux itself (the physical Menu OK / Back, triggers, stick clicks) knows nothing of the OSD: Screamer 2's menus confirmed and went back with the OSD's Cross and Circle. The core puts `OSD_STATUS` (1 for the OSD menu, not its info boxes) in bit 22 of the status word 1, `MH_OSDOpen()`, and the library holds everything back meanwhile: in `MH_ReadInput()` (buttons, keys, sticks, mouse buttons; the mouse's movement left out) and in the Linux reads (`mh_osd_hold()`); what is held when the OSD closes stays released until it is let go. A game needs no code for it. Cores built before have the leak: build them again.
- *Menu OK* / *Menu Back*: `MH_MenuButtons()` (`hps/mister_joymap.c`), which the SDL driver calls every frame, looks every two seconds whether the controllers (`/proc/bus/input/devices`), `config/` and `config/inputs/` or the mapping files it read have changed, and reads the mapping files again only then. Reading them every time stopped the game for 10 to 20ms (found with the YQuake2 core, 2026-10-15). Cores built before that have that stall every two seconds: build them again. The mapping files are found under the name Main_MiSTer loaded (`MH_MappingName()`, `/tmp/CORENAME`), not `MISTER_HYBRID_SET`. A physical OK / Back button that drives no core button (one without a function in that core, which MiSTer then passes to the core not at all) is read from Linux, as the stick buttons are: `MH_MenuButtonsPressed()`, which the SDL driver uses for its Menu OK / Menu Back buttons (found with Dethrace on a DualSense, 2026-10-16: Back on Circle, which had no race function). Cores built before have no Menu Back on such a button: build them again.
- *FPS Counter* (status bit 15, `"O[15],FPS Counter,Off,On;"` after *Stereo Mix*) is in every core's OSD too. The library draws it (`fps_stamp()` in `hps/mister_hybrid.c`, into the copy of the frame the core shows, RGB565 or 8bpp): a game needs no code for it, only the line in its `CONF_STR` and a build against this library. No change to the FPGA side. Cores that predate it (2026-10-12) get it at their next build: add the line. `MISTER_HYBRID_FPS=0` (or `1`) in the game's environment hides (or shows) it whatever the OSD says: for screenshots without it.
- Status bits 0..23 of the OSD mean the same in every core (16..23 unused since host version 14); a game's options start at bit 24. Triggers (`T`, a cheat, "next level") are bits 56..59 only, read with `MH_OSDTriggers()`: a trigger's pulse is too short for the game to see, the core flips the bit instead.
- A core with several games picks one with `MH_PickGame()` (`hybrid/README.md`, "Several games in one core"): each game a menu entry (set name `<core>_<id>`), shareware without one; the list only of the games that are there. Settings and button mappings are per game (`MH_SetName()`).
- **Rule: the purple screen ignores *Horizontal Size*** (Danik, 2026-10-16). The core's own picture (logo, messages, game lists) is always shown at size 0, whatever the player set on the *CRT Options* page for the game: nothing is at its edges, and a small size makes its text hard to read. `hybrid_host.sv` takes the size only while a game has the screen (`game_on`); the positions still apply. Keep it that way in any change to the video timing, and test the core's picture with the size at -24 when it changes.
- **Rule: messages fit in 4 lines of 71 characters** (`MH_MSG_ROWS`, `MH_MSG_COLS`; `hybrid/README.md`, "Messages"). Every message a game shows (`MH_UI_Message()`, `MiSTer_ShowError()`) is written for that space: what is wrong and what to do, with the path from where the game runs (`games/dnk/<Engine>/`), no empty lines. Check each one with `tools/make_wall.py --preview out.png --message "..."` when a core is built against host version 13 or later; messages of cores from before were written for 36 characters and empty lines and need going over.
- **Rule: every port starts the same way** (Danik, 2026-10-16: "a UX as unified as possible"). The core's purple screen with its intro; the game waits for the intro's end (the library does). The game is the menu entry's (`MH_PickGame()`), or from the core's list of the games that are there when the core was started by itself (one there: that one; none: the message naming the files and where they go). From the moment the game is known until its first frame the purple screen says **`Loading <title>...`**, the title as in `package/games.txt` (`MH_UI_Message(title, text, 0)` right after `MH_PickGame()`, as `MiSTer_PickGame()` of `template/game/mister_port.c` does; a port with its own pick code adds it). Quitting a game picked from the list brings the list back (exit code 42), otherwise the MiSTer menu. Check it on the MiSTer for every game with `tools/test_on_mister.sh`.
- **Rule: look for cheats and offer them for the OSD** (Danik, 2026-10-16). For every core, new or built again, find the cheats each of its games has (typed words, key combinations, console commands, test switches of the source port) and, in the plan made before building, list them for Danik with what each does and ask which go on the core's *Cheats* page (`"P2,Cheats;"`, after the game's options). A cheat that stays on is an option (`O`), one that does something once is a trigger (`T[56]`..`T[59]`, `MH_OSDTriggers()`; only four, so in a core with several games the games can share them, each hiding the lines of the others with `MH_SetMenuMask()`). Cheats a pad cannot reach (typed on a keyboard) are the ones most worth offering.
- **Rule: menus work with Menu OK and Menu Back** (Danik, 2026-10-17: "the menus must work with Mister_OK = OK, Mister_Cancel = Cancel"). In every menu a port has (the game's own, the port's pages, questions), *Menu OK* confirms and *Menu Back* goes back: the MiSTer menu's (SDL buttons 28 / 29 of joystick 1, `MH_MenuButtons()`) and the core's own *Menu OK* / *Menu Back* of its `J1` list (buttons 8 / 9), besides Start / Select where the game has them. A game action (accelerate, brake, fire, a trigger) does not confirm or go back in a menu: with *Menu OK* on a button that also has a game action, the menu must do what *Menu OK* says (OpenScreamer's Screamer 2 went back, its brake being ESC there, and confirmed with the gas; 2026-10-17). Where a port turns buttons or the stick into keys, every key that goes down also comes up (a menu that keeps keys held otherwise sees an arrow held for ever: Screamer 2's gearbox jumped back to AUTOMATIC when the stick came back to the middle). Check every menu on the MiSTer with *Menu OK* / *Menu Back* on buttons that are also game actions (the MiSTer menu's, in *Define joystick buttons*; up to host version 13 the core's OSD options), and with the stick as well as the d-pad. Each core does this itself, by hand, in its own input code (Danik, 2026-10-17): the framework only delivers the buttons and sends no keys for them, because the cores already map 28 / 29 each in their own way (a key, a mouse click) and in-game the same buttons have game actions. Check it in every core when it is built again.
- **Rule: players copy whole folders** (Danik, 2026-10-18). A README tells the player to copy the game's folder, or its folders, whole and as they are ("everything in the game's folder"), even where that copies files the port never reads; it never names files that can be left out or deleted. The port's check of its data looks for every file the game opens (one that is only looked for, not read through, is enough where reading it costs time at every start): OpenScreamer's README said which Screamer 2 files were not needed, a player took out one too many, and the menus were black without a message (2026-10-18). Check it in every core when it is built again.
- **Rule: missing game files are said on the purple screen** (Danik, 2026-10-16). A game that cannot start because its files are not there never just quits, and never leaves it to the log: it shows a message that waits until the player leaves the core (`MH_UI_WAIT | MH_UI_ERROR`, or `MH_PickGame()`'s `missing` and `none`), and that message says clearly, within the 4 lines of 71, **which files** (by name or pattern: `*.WL6`, `valve/pak0.pak`), **for which game** (in a core with several), and **where they go** (`%s`, `MH_GamePath()`: `games/dnk/<Engine>/`, or `usb0/games/dnk/<Engine>/` from a USB drive; so no "on the SD card" after it, which the messages of the cores before host version 14 have). "Copy the game's files" alone is not enough. Every game of every core, new or built again; check each menu entry on the MiSTer with its data taken away.

## FM music

- A game whose music was made for an AdLib / OPL2 chip sends the chip's register writes to the core (`MH_FMWrite()`, host version 10; `hybrid/README.md`, "The FM chip") and does not run a software chip on the ARM, except as the fall-back for a core without the chip.
- `rtl/jtopl/` is JTOPL commit 7ac0c81 with SIX changes of ours, each marked `HYBRID:` (in `jtopl_op.v` the feedback's strength; `jtopl_eg_final.v` key scaling levels 1 and 2 swapped; `jtopl_eg_step.v` rate scaling halved, and attacks twice too fast; `jtopl_eg_ctrl.v` the release's extra half step; `jtopl_eg_pure.v` the four fastest decays; `jtopl_acc.v` a per-channel volume test its author left in). All were found by comparing with Nuked OPL3, which is taken from the chip's die: `sim/fm_song.sh <log> <out>` plays a log of register writes (`FAKECORE_FMLOG=<file>` makes fakecore write one from a running game) on both with Verilator, 25 seconds of music in 20. Do not edit `rtl/jtopl/` otherwise; when replacing it, carry the changes over or check each is no longer needed, with that tool. Still different from the chip, slightly: attack rates 1 to 3, the shape of the tremolo, and about 2dB less of the upper harmonics of a note that is dying away.

## Rules

- The launcher `launcher/danik_hybrid_ports.sh` is developed only here. Raise its `VERSION` with every change that reaches users and keep the contract in its header working for ports already released. A launcher change reaches players through the database alone (`launcher/distribution.py publish <checkout>`, no zip: the database's launcher and screen are always this repository's), no port packaged again. `launcher/danik_hybrid_cores.sh` is the launcher before, in its last version (3): it comes with every port as `games/dnk/danik_hybrid_cores.sh`, where a running version 2 installs it, and hands over to the new one (`danik_hybrid_ports.sh takeover`; `hybrid/README.md`, "The launcher"). It is not changed again; the new launcher keeps `takeover`. Test changes on a copy of an SD card (`DANIK_HYBRID_ROOT`, `DANIK_HYBRID_TMP`), on the PC and in `/tmp` on the MiSTer, never on the player's own setup.
- **Naming and layout** (`hybrid/README.md`, "Naming and layout on the SD card"): `dnk` for what is on the SD card (`_Other/dnk-<Game title>.mgl` for every game, `_Other/dnk/dnk-<Engine>_YYYYMMDD.rbf`, `games/dnk/<Engine>/`, `logs/dnk/<Engine>/`) and the repository `dnk_Distribution_MiSTer`; `danik` for the script (`danik_hybrid_ports.sh`) and the database id (`danik_hybrid_ports`). Script names on the MiSTer keep the `danik_` prefix.
- **The engine's name** (the core's `CONF_STR` name and its folders) is the source port's, never a game's alone; agree it with Danik before a new core is started, with the games' menu titles and ids. A game's set name is `<Engine>_<Game>`, short, no spaces, 31 characters at most.
- **The games of a core** are in its `package/games.txt`, and only there. `package.sh` ships it as `games/dnk/<Engine>/games.txt`; `launcher/distribution.py` makes the launcher's catalogue (`Scripts/.danik_hybrid_ports/catalogue.txt`) from those of the published ports, so the launcher's screen offers only what the database has (Danik, 2026-10-16: never a port that is not published). A new port or game changes no launcher. A core whose `package.sh` predates this (2026-10-16) adds the line from the template's (`games.txt` into the game's folder) and is packaged again before it is published: `distribution.py` refuses its zip otherwise.
- **The database** comes through Downloader's drop-in file `downloader_danik_hybrid_ports.ini` (`launcher/`, in every zip); the launcher's screen writes only that file, never `downloader.ini`. It is made only with `launcher/distribution.py` (`hybrid/README.md`, "Distribution"), never by hand.
- **Rule: publishing is its own step** (Danik, 2026-10-16). A port goes into the database (`dnk_Distribution_MiSTer`, which update_all installs from) only when Danik asks for it ("publish <port>"), never as part of a release, a build or a test: unannounced ports are released into their own `releases/` and stay out of the database and off the launcher's screen. Publishing: package the release with the current `hybrid/`, then `hybrid/launcher/distribution.py publish ~/dnk_Distribution_MiSTer releases/<Engine>_YYYYMMDD.zip` (a local commit; it refuses what does not add up), test the database (`hybrid/README.md`, "Testing the database") when the tool or the launcher changed, and `distribution.py push ~/dnk_Distribution_MiSTer` only when Danik says so. Taking a port out: `distribution.py remove`.
- **Tags** of the database: `launcher`; an engine's files `<engine>` and all its games' tags; a game's menu entry `<engine>_<game>` and `<engine>`; different from each other also without `-` and `_`.
- **Players read "hybrid ports"** (READMEs, the launcher's screen); the framework itself stays "hybrid core" (`Hybrid_MiSTer`, the `MH_` library, "Hybrid Core Framework").
- Game data goes into the core's own folder, `games/dnk/<Engine>/`, unless a core has a reason for another; messages name it from where the game runs (`MH_GamePath()`).
- **Rule: game data can be on a USB drive** (Danik, 2026-10-18, a player's request; host version 14). The launch script's `DATADIR` is the first of `/media/usb0`..`usb7/games/dnk/<Engine>/` that exists, else the SD card's folder, and wins whenever it is there, also with files missing (the message then names it). The game runs in `DATADIR` and finds its data, settings and saved games there; the programs, the libraries the game loads and the rest of what the port brings stay in `GAMEDIR` on the SD card (USB drives are mounted `noexec`, and Downloader installs there). Each port's `GAME:` line passes what it needs (a data folder from `$DATADIR`, a library folder from `$GAMEDIR`); a game that looks next to its own program for data or libraries needs both. `hybrid/README.md`, "Naming and layout". Test every port with `TEST_USB=1 tools/test_on_mister.sh` too (every game id and `nodata`). Every core built again with host version 14 takes the template's launch script and test script.
- MiSTer Frontier by MiSTer Organize is credited and thanked for the inspiration in every core's `README.md`, package `README.txt` and launch script header. Our launcher does not depend on it.
- Game data is never committed or shipped.
- **Rule: test on the MiSTer with `tools/test_on_mister.sh`** (Danik, 2026-10-16). Every core has it (`template/tools/test_on_mister.sh`; stamped by `new_core.sh`, copied into an existing core when it is built against host version 13 or later). It runs what `./package.sh` makes with the port's own `danik_hybrid_launch.sh`, from `/tmp/<name>_test` next to what is installed: the installed game's folder mirrored (links to its files, copies of those under 1MB, so that what the game writes stays in `/tmp` and a big game fits; a game with more small files than `/tmp` holds names the ones it writes in the script's `COPY`, a `GAME:` line: Xash3D, 2026-10-17), the core in a hidden `_Other/.<name>_test/`, the set name `<Engine>_TEST` for the OSD settings, the core's default button mappings (the installed port's are not copied, and one made in an earlier test is removed at every start; Danik, 2026-10-17); no launcher is touched, and `stop` removes all of it. Before a core is called working or released, try with it, on the MiSTer: every game of `package/games.txt` (`<id>`), `list`, `nodata`, a game whose data is missing, and quitting a game picked from the list (the list comes back); `stop` at the end. It is also how Danik tries a build. It needs the launch script to be the template's (`GAMEDIR=`, `DATADIR=` and `RUNLOG=` lines). `TEST_USB=1` puts the game's data on the first USB drive, in `games/dnk/.<Engine>_test/` (a copy of the installed data, made at the first such test), and `stop` removes it.
- **Rule: no GitHub releases** (Danik, 2026-10-16). Players get the ports through the database of `dnk_Distribution_MiSTer` (update_all), which makes GitHub releases redundant. A release is `<Engine>_YYYYMMDD.zip` from `./package.sh`, copied to the repository's `releases/` folder, committed and pushed; that is all "release" (or "commit, push, release") means. It does not put the port in the database: that is publishing (the rule above). No GitHub release, no tag, no zip attached anywhere else, also not when asked to "release". The GitHub releases made before stay as they are.
